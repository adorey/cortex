# 🚀 Cortex v0.4.1 — Reuse before create

> *"Every dependency is a liability."* — Ford Prefect, who would rather add a parameter than a file.
>
> An agent asked to "back up this database" happily writes a new playbook. The existing one already took the database name as a variable. Both then drift, and only one gets the next fix. This release makes checking for that a step of the protocol, not a matter of taste.

## Highlights

### ♻️ New dispatch-protocol step — reuse check

`agents/roles/prompt-manager.md` gains a step between the workflow lookup and the dispatch: when a request implies creating a **script, playbook, command, job, module or configuration file**, look first for an existing asset that already covers the case **by configuration**. The outcome is announced either way — reused (and how) or genuinely new (and why).

The step is backed by a new `♻️ Reuse Before Create` section in the same role card:

1. **Find the candidates** — assets doing something adjacent (same directory, same tooling, same naming family).
2. **Read what they already accept** — variables, parameters, profiles, flags. Internal tooling is usually more parameterisable than it looks.
3. **Decide out loud** — fits by configuration → deliver *the configuration* (extra vars, job template, profile entry) and say no code was needed; capability genuinely missing → write it, and state which existing asset was checked and why it does not fit.
4. **Ask the owner** when the asset belongs to another team (ops, infra, data) before adding a file to their repository.

It names the anti-pattern too — **the "safer copy"**. *"A new file cannot regress the existing one"* is a rationalisation: the duplication **is** the regression risk. A parameter added to a shared asset benefits every caller; a fork benefits nobody.

The section closes by pointing the rule back at cortex itself: before adding a role, capability or workflow, check whether an existing one should be extended or overlaid instead.

## Why a protocol step and not a role principle

`platform-engineer.md` already carries a *Minimal dependencies* principle, but it is about **adding third-party packages**, and it is only loaded when that specific expert is dispatched. Reusing an existing internal asset applies to every implementer — backend, data, infra, QA — so it belongs in the always-read Prompt Manager card, ahead of the dispatch decision. A rule that arrives after the expert has been chosen arrives too late to change what gets written.

## Breaking changes

None. The step adds a check before dispatch; existing workflows, roles, capabilities and overlays are untouched. Host projects inherit the behaviour with no migration.

## Field note

The rule comes from a real rejection: a `dbDumpCity.yml` playbook was written to back up an additional database, and the ops reviewer pointed out that the existing `dbDump.yml` already accepted the database name, host, port, S3 provider and bucket as variables. The correct deliverable was a job template — a configuration, not a file. The playbook was withdrawn.
