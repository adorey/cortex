# 🚀 Cortex v1.1.2 — Know Where Your Towel Is

> *"Any man who can hitch the length and breadth of the Galaxy, rough it, slum it, struggle against terrible odds, win through, and still knows where his towel is, is clearly a man to be reckoned with."* — The Hitchhiker's Guide to the Galaxy, on towels.
>
> 1.1.1 showed the way out of the submodule to a teammate who pulled its removal. The counter-review that checked it found four rougher roads, older than the fix: a submodule added over a clone, one staged and never committed, one in a linked worktree of the project, and the work only a stash or the reflog holds. This patch release covers them: on every way out, Cortex now knows where the submodule's repository is.

## Fixes

### 🗂️ A submodule whose repository is its own `.git` directory ([#157](https://github.com/adorey/cortex/issues/157))

`git submodule add`, run on a clone of Cortex already at `cortex/`, keeps that clone's `.git` directory, as older git did for every submodule. These cases went wrong:

- **The migrator's clone.** Before git 2.35, `git submodule deinit` refuses that repository; from then on, it moves it under `.git/modules/cortex` before emptying `cortex/`, and the commands `cortex init` printed never removed it there. They now begin with `git submodule absorbgitdirs cortex`, which moves the repository there on any git since 2.12, and end with its removal, at the path git itself names: `git rev-parse --git-path`, which is under `.git/worktrees/<worktree>/` in a linked worktree. The name under `.git/modules/` is the one git gives the submodule, read by git from the `.gitmodules` at the top of the repository; and if a repository is in that place already — an earlier submodule's, which `git rm` keeps, or another one's — git cannot move `cortex/.git` there: Cortex says so, names the place, and prints no command that would fail, nor a removal that could only reach the wrong repository.
- **The developer who added the submodule that way, after pulling its removal.** With `.gitmodules` gone and a `.git` directory in `cortex/`, it was taken for a plain clone. It got `rm -rf cortex` with none of the checks, and the submodule's section stayed in `.git/config`. A `.git` directory in a project whose settings still hold that section is now a submodule left behind: the teammate's checks, then the section's removal. A clone made beside a submodule that `git mv` took elsewhere stays a clone: `.gitmodules` gives the section to that submodule.
- **A submodule staged and never committed.** `git rm cortex` refuses it, and the printed `git rm -f .gitmodules` then left a staged submodule with no `.gitmodules`. It now gets `git rm -f cortex`, which git requires there.
- **A project in a subdirectory of its repository.** git names its submodule by its path from the top — `app/cortex` — and Cortex now asks git for that name, where it read the project's own `.gitmodules`. The removal of the submodule's settings a teammate gets after the pull names that section too: 1.1.1 named `submodule.cortex`, which could be another submodule's, at the top of the repository.

### 🌳 A submodule in a linked worktree of the project ([#158](https://github.com/adorey/cortex/issues/158))

In a `git worktree` of the project, a submodule's repository lives under `.git/worktrees/<worktree>/modules/cortex`. Cortex read any `/worktrees/` in that path as "`cortex/` is a worktree of another repository", and printed a `git worktree remove` that could not work. It now tells the two apart as git does: a worktree of another repository has an administrative directory, which holds a `commondir` file, and a submodule's repository never does — so a project in a directory named `worktrees` is not taken for one either. A developer who works in worktrees gets the submodule's commands — the migrator's or the teammate's — like anyone else.

### 🧺 What a stash or the reflog holds ([#160](https://github.com/adorey/cortex/issues/160))

Before printing `rm -rf` for a teammate's leftover `cortex/`, Cortex prints checks that it holds nothing of theirs. Two cases slipped through:
- a commit made on a detached HEAD, then left behind by a `git submodule update`, which only the reflog holds;
- a stash.

The second check now walks the reflog too, and a third lists the stashes:

```bash
git -C cortex status --short --ignored -- . ':(exclude)agents/personalities/.active-*'
git -C cortex log --format='%h %an: %s' HEAD --branches --reflog --not --remotes
git -C cortex stash list
```

On a clean clone, the first and the third print nothing. The second shows each commit's author: besides the commits you left behind, the reflog keeps commits that no Cortex branch holds any more, rewritten or deleted upstream, and no git option keeps them out. The author tells them from yours.

The migrator gets the same three checks when the submodule's repository is its own `cortex/.git`: that clone, made a submodule in place, is the likeliest to hold work of theirs, and the commands of #157 now remove it.

### 🏷️ `cortex init` names no sync it never ran ([#159](https://github.com/adorey/cortex/issues/159))

`cortex init` runs the same checks as `cortex sync`, and its refusals named sync, and told you to run *cortex sync* again:
- a link at `cortex/` Cortex did not make;
- an unreadable `.synced`;
- a copy holding files of yours;
- a sync that lost a race or waited too long for the lock.

Run from `cortex init`, `cortex sync` alone does not finish the job. They now name Cortex, and tell you to run *the command* again.

## Upgrading

1. Install the binary again — the install line installs the latest.
2. Set `version = "1.1.2"` in `cortex.toml`.
3. Run `cortex sync`.

Nothing else changes.

## Notes

- **Each fix comes with a test that fails without it,** checked by mutation. For #157, the printed commands are run, and git's state is checked afterwards; the suite passes with git 2.30 too.
- **The four issues were found by the counter-review of 1.1.1's fix,** the `code-review` workflow's step B6, and proposed there as out of scope: older than that fix, they waited for their own release.
- **On Windows,** the linked-worktree test first failed on a path with an accent. Cortex was right; the test read git's UTF-8 output in the console's code page, and now reads it as UTF-8.
