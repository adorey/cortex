# 🚀 Cortex v1.1.1 — Unpleasantly Like Being Drunk

> *"You'd better be prepared for the jump into hyperspace. It's unpleasantly like being drunk."*
> *"What's so unpleasant about being drunk?"*
> *"You ask a glass of water."* — Ford Prefect and Arthur Dent.
>
> Moving to 1.0.0 was a jump, and for part of a team an unpleasant one. A teammate whose clone had the submodule initialised pulled its removal, and `cortex sync` sent them to three commands that could not run, then refused again. This patch release makes that jump the one it was meant to be, and puts two smaller things right with it.

## Fixes

### 🧭 A teammate who pulled the submodule's removal ([#147](https://github.com/adorey/cortex/issues/147))

**What the pull leaves.** It removes the submodule from the index, and keeps the rest:
- `cortex/`, with its files;
- the submodule's repository under `.git/modules/`;
- its section of `.git/config`.

The commands `cortex sync` printed — `git submodule deinit`, `git rm` — fit the migrator's clone only, where `cortex` is still in the index. On the teammate's they had nothing to act on.

**What `cortex sync` does now.** It asks git which of the two states the clone is in, and prints for the teammate what removes what the pull left.

- **First, two checks,** to make sure the directory holds nothing of theirs: `git -C cortex status --short --ignored`, for the files changed, added or ignored in it — but the theme marker `setup.sh` wrote there, which nothing reads now — and `git -C cortex log --oneline HEAD --branches --not --remotes`, for the commits no remote branch holds.
- **Then the commands.** They are printed, never run: Cortex deletes nothing it did not write.
- **If the teammate already ran the commands 1.0.0 or 1.1.0 printed,** the one that worked removed the submodule's repository. git can then show nothing of `cortex/`, and `cortex sync` says so, instead of offering checks that would fail.
- **Without git to ask,** it prints the migrator's commands, as before.

The migration guide's §4 now covers both sides of the pull:
- **after it:** the commands `cortex sync` prints;
- **before it:** `git submodule deinit -f cortex` and `rm -rf .git/modules/cortex` are enough — the pull then removes the empty `cortex/`, and `cortex sync` passes the first time.

### 🗂️ No empty `.gitmodules` left behind

`git rm cortex` removes the submodule's section of `.gitmodules`, and keeps the file, empty and tracked. When `cortex` was the only submodule, the commands `cortex init` prints now end with `git rm -f .gitmodules`. A project that already committed the empty file can remove it the same way.

### 🔐 A binary carries no pre-release's checksum ([#151](https://github.com/adorey/cortex/issues/151))

Each binary embeds the checksum of every spec archive released before it. The pre-releases were in that table too: 1.0.0 and 1.1.0 knew `0.0.0-alpha.1`'s, a version none of them serves. A pre-release is thrown away, or built again under its tag, and a checksum kept for it would have every binary built meanwhile refuse the new build. From 1.1.1, the table holds releases only. A pre-release is checked against its release's `SHA256SUMS` alone, like a release newer than the binary.

### And two smaller ones
- **`cortex init` names itself.** Refusing a `cortex/` Cortex did not write, it said *which cortex sync did not write* — it now says Cortex.
- **The CLI suite no longer breaks when a theme is added** ([#148](https://github.com/adorey/cortex/issues/148)). A test listed the shipped themes by hand; it now reads them from the spec it runs on.

## Upgrading

1. Install the binary again — the install line installs the latest.
2. Set `version = "1.1.1"` in `cortex.toml`.
3. Run `cortex sync`.

Nothing else changes.

## Notes

- **#147 was found in use.** It came from moving a real project from its submodule to 1.0.0, then replaying the teammate's side of the move. The fix was checked on that same path: a migrator's clone, a teammate's clone with the submodule initialised, and a pull between them, where the printed commands are run and `cortex sync` then passes. Three rounds of counter-review, before it merged, found the cases the first version missed, each now with its own test: a teammate who had already run 1.0.0's commands, commits on another branch of the submodule, setup.sh's theme marker, and a submodule whose repository is its own `.git` directory.
