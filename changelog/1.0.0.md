# 🚀 Cortex v1.0.0 — So Long, and Thanks for All the Fish

> *"So long, and thanks for all the fish."* — the dolphins' last message, left just before the Earth was demolished.
>
> Since 0.1.0, every project carried its own copy of Cortex — a submodule or a clone at `cortex/` — and two scripts to set it up and check it, one of them needing a Python on the path. They leave in this release, with thanks. What takes their place is one command, installed in one line and needing no Python; one copy of the spec per machine and per version, read-only, checked against the checksums its release published; and in each project a `cortex.toml` that says which version it uses. The way a project uses Cortex changes, hence 1.0.0 — and from here on, what a version promises is written down.

## Highlights

### 📦 One command, installed in one line

**`cortex`** is a native binary for Linux (`x86_64` and `aarch64`, glibc 2.28 or later), macOS (Apple silicon) and Windows (`x86_64`), built with PyInstaller, embedding its interpreter: the machine needs no Python ([ADR-008](../docs/adr/ADR-008-cortex-binary.md)).

```bash
curl -fsSL https://raw.githubusercontent.com/adorey/cortex/main/install.sh | sh      # Linux, macOS
```

```powershell
irm https://raw.githubusercontent.com/adorey/cortex/main/install.ps1 | iex           # Windows
```

- **What the scripts check.** Both verify the archive against the release's `SHA256SUMS`, download over https only — every redirect too — and run the binary before putting it in place: one that cannot run here, on an older glibc or from a `noexec` directory, is never installed.
- **Where it goes.** The command lands in `~/.cortex/bin`, named `cortex-ai` when another `cortex` comes first on `PATH` — the Cortex Labs CLI and the Prometheus-compatible server are both called that.
- **Traced to its build.** Every asset carries a build-provenance attestation, and so does each binary inside its archive: `gh attestation verify ~/.cortex/bin/cortex --repo adorey/cortex` checks the installed file itself.
- **Built from pinned tools.** The build tools are pinned by hash and the workflow's actions by commit, and the archives are dated by the commit.

### 🗄️ One spec per machine, one `cortex.toml` per project

The spec lives in **`~/.cortex/versions/X.Y.Z`**, read-only. The binary writes its own version from itself; any other version is downloaded from its release's spec archive, then checked twice: against that release's `SHA256SUMS`, and against the checksum the binary carries for it. Every binary embeds the checksum of each spec archive released before it — `cortex --version --verbose` prints them.

A project commits a **`cortex.toml`** — its `version` and its `theme`. **`cortex sync`** writes in `cortex.local.toml`, which git ignores, where the spec is on this machine. It brings the spec to the project in one of three modes:

| Mode | In the project | For |
|---|---|---|
| `store`, the default | nothing: the spec is read where it is kept | tools that read outside the project when told where |
| `link` | `cortex/`, a symbolic link — a junction on Windows, which needs no administrator right | tools that read only inside the project |
| `copy` | `cortex/`, a read-only copy | a file system without links, or a tool that does not follow one |

`cortex/` becomes a name — the directory `spec` names — so the spec's text and every overlay's `Base: cortex/agents/…` header stay as they are.

A sync is made to fail safely:
- **It checks everything before it changes anything.** It stages the new `cortex/` beside the old one and puts it in place with one rename.
- **It deletes nothing it did not write:** a submodule, a clone or any other directory at `cortex/` is refused.
- **Two syncs of one project wait for each other.**
- **It tidies up after an interrupted sync**, removing what that sync left behind.

`--from PATH` points a project at a checkout instead — the contributors' test loop.

### 🧰 `cortex init` — `setup.sh`, at parity

**Same as `setup.sh`:** the same options, and the same files at the same paths, byte for byte. A parity matrix captured from the script is replayed on every platform.

**Deliberate differences:**
- **`--service NAME` is repeatable**, so a workspace initialises unattended.
- **An instructions file that is already there is kept, unless `--force`.** `--force` keeps the file it replaces as `FILE.bak`, never overwriting a backup.
- **A project whose `cortex/` is a submodule or a clone is refused**, with the commands that remove it — printed, not run, since they rewrite your git state.

**Notes on a kept instructions file.** Init says when that file holds no Cortex bootstrap, holds one older than this release, or was written for the other layout.

### ✅ `cortex validate`

Same checks, same report, same exit codes as `bin/validate-overlays.sh`, against the spec the project synced — and it refuses, exit `2`, a spec synced for another version than `cortex.toml` pins. Its report is the same on every platform: paths with `/`, files listed in name order, UTF-8 whatever the console's code page.

### 🔓 Claude Code, without the permission prompt

Claude Code reads outside the project only with permission — once per session in `store` mode, and in `link` mode too, since it checks where a link resolves. With **`claude_access = true`** in `cortex.toml` — `cortex init --tool claude --claude-access` — or `cortex sync --claude-access` for one developer, sync keeps the store's path in `.claude/settings.local.json`. It keeps that one entry only: a developer's own entries are never touched. Measured with Claude Code 2.1.273: the Prompt Manager's card is reached with no prompt at all.

### 🏃 The runtime reads the store

A project with a `cortex.toml` gives the runtime its base through the store ([ADR-002 §9](../docs/adr/ADR-002-cortex-runtime.md#9-amendments)):
- **The version is fixed at acceptance.** The runtime reads it when a run is accepted, and names it in the answer as `cortex_version`.
- **`deploy/compose.yaml` mounts only the store's `versions/`**, read-only, from `CORTEX_STORE_PATH`.
- **A version the store lacks is refused**, with `422`.

A project without a `cortex.toml` resolves as before.

## Upgrading

The whole path, with every command for Linux, macOS and Windows, is in [the migration guide](../docs/migrating-to-the-binary.md). In short:

- **Install the binary** once per machine, with the line above.
- **A single project, from a submodule:** `cortex init` prints the three commands that remove the submodule; run them, then `cortex init --tool <your tool> --force`. Carry over what you added by hand from `FILE.bak`, delete it, and commit `cortex.toml`, `.gitignore` and the instructions file.
- **A workspace, from a clone:** check first that the clone holds nothing of yours. Files added to a clone are not in the store: an overlay built on one fails with `BASE_NOT_FOUND`, and a workflow that calls a role or a character only the clone had loses it — `validate` does not see that part. Move the clone away, then `cortex init --workspace --tool <your tool> --force`. A workspace root that is no git repository has nowhere to commit `cortex.toml`: each developer runs `cortex init` in their own.
- **Every other developer**, after a pull: `cortex sync` — as they would run `npm install`.
- **The theme** is `theme` in `cortex.toml`, and a developer's own in `cortex.local.toml`: the `.active-theme` marker is gone. A developer who chose a theme with `setup.sh` chooses it again.
- **CI** installs the binary of the version `cortex.toml` pins, then runs `cortex sync && cortex validate --strict` — the guide has the lines, for a shell and for PowerShell.
- **The runtime:** run `cortex sync` in the project, and set `CORTEX_STORE_PATH` in `deploy/.env` to your store.
- **A project pinned to the pre-release `0.0.0-alpha.1`:** set `version = "1.0.0"` in `cortex.toml`, then `cortex sync`. This release refuses the pre-release's spec.

## Notes

- **ADR-008 is Implemented.** Its §9 records, phase by phase, what changed during the implementation and in the five rounds of review that followed it.
- **Tried on two real projects before the release,** on the pre-release `0.0.0-alpha.1`: a single project leaving a submodule, and a workspace of a dozen services leaving a clone.
- **Only Claude Code is measured** so far. GitHub Copilot, Cursor and Codex start in `store` mode; switch to `link`, then `copy`, if a conversation does not reach the Prompt Manager's card. Measuring them is [#137](https://github.com/adorey/cortex/issues/137).
- **The Windows executable is not code-signed.** Installed by `install.ps1`, it carries no Mark of the Web, and SmartScreen does not stop it.
- **Releases are made by pushing their tag.** The workflow builds the four binaries, runs each Linux one on the oldest glibc it supports, and creates the release as a draft. It attaches every asset, and only then publishes. A pull request of a stack runs the tests from source. The binaries are built where code integrates: on its release branch, and on the pull request from that branch into `main`.
