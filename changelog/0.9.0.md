# 🚀 Cortex v0.9.0 — Beware of the Leopard

> *"It was on display in the bottom of a locked filing cabinet stuck in a disused lavatory with a sign on the door saying 'Beware of the Leopard.'"* — Arthur Dent, on where the plans to demolish his house had been "on display".
>
> Cortex has a roadmap now — fifteen decision records, from a unified cascade resolver to a hosted offering — and this release is about not keeping it in a locked filing cabinet. It ships no new behaviour for the agents a host project runs. It ships the way the next decisions get delivered: one epic per ADR, in the open; one reviewable pull request per phase; and the two traps that cost real time on the project this process comes from, written down before they cost it again.

## Highlights

### 🗺️ The roadmap, in the open

The next ADRs are now **epics** in the issue tracker — [#36](https://github.com/adorey/cortex/issues/36) (ADR-007, Cortex Core) to [#50](https://github.com/adorey/cortex/issues/50) (ADR-021, the hosted offering), plus [#51](https://github.com/adorey/cortex/issues/51) for a security scan that can jump the queue. Each one states its **one** decision, what it **excludes**, and what it depends on. The dependencies are native *blocked by* links, so the order is enforced by the tracker rather than remembered.

Numbers beyond ADR-008 are provisional: numbering is strictly sequential, so writing an ADR out of order shifts every number above it. What is committed is the order and the boundaries, not the digits.

### 🧱 One pull request per phase, stacked

New **`docs/process/adr-implementation.md`** — the mechanics for delivering an ADR too large for a single pull request:

- **an integration branch per ADR** (`release/adr-NNN-slug`), with the ADR text as the *first* pull request of its stack, so the decision is reviewed before the code that implements it;
- **one pull request per phase**, each stacked on the previous one — not one per task, which would turn every review comment into a dozen restacks;
- **four levels of issues** — epic → milestone → phase → task — tasks being native sub-issues, so the board reads as a changelog once the work is done. The phases of an ADR are created when the ADR is accepted, never earlier: issues written ahead of their decision rot.

### 🔁 A generic `adr-implementation` workflow

New **`agents/workflows/engineering/adr-implementation.md`** — eight steps for one phase: dispatch, technical breakdown, implementation, QA, performance audit, security audit with active probing, documentation, pull request. A step that finds a defect sends the phase back to implementation rather than opening a follow-up on a later phase, because the stack would carry the defect upward.

It is **stack-agnostic** on purpose. The checklists defer to `project-context.md` and the loaded capabilities for a stack's own rules; a project that wants those rules spelled out in the steps overrides the file — workflows use replacement, not additive overlays.

### ⚠️ Two traps, written down

- **Closing keywords do not fire inside a stack.** GitHub closes a linked issue only when a pull request merges into the default branch, and every pull request of a stack targets the branch below it. The final pull request into `main` must repeat the whole `Closes` list — on the project this process comes from, sixty-four issues stayed open through a release because it did not.
- **A pull request inside a stack is merged with a merge commit.** Squashing, and GitHub's *Rebase and merge* — which also creates new commits — leave every branch above built on commits that are no longer there. `CONTRIBUTING.md` used to prescribe "squash on merge" for everything; it now tells the two cases apart.

### 🏷️ Labels that show the firewall

`bin/setup-labels.sh` creates the tracking labels, idempotently. The `type:` labels split along the ADR-002 firewall — `type:spec` for the Markdown cascade, `type:core` for cortex-core and the CLI, `type:runtime` for the engine — so a task that straddles it shows on the board, and is usually two tasks. The roadmap *wave* is deliberately not a label: it moves with every re-plan, so it is a field of the roadmap board instead.

### 📛 Release names, written down

Every release since 0.1.0 has carried a name, and every note an epigraph. `CONTRIBUTING.md` now says so, so the custom outlives the memory of whoever started it.

## Notes

- **No runtime behaviour changes**, no change to the cascade contract. Host projects gain one generic workflow, to use as it is or to override.
- ADRs delivered in several steps now end with a numbered **Phases** section; an ADR whose every phase has merged moves to the new `Implemented` status.
- Contributor-facing: issue templates for ADR epics, phases and tasks, a pull request template, and `#<issue>` before the commit subject for ADR work.
- The workflows index now lists `frontend-testing` and `support-triage`, which existed but were missing from it.
- `CONTRIBUTING.md`'s release process now describes how releases are actually made — an integration branch, artefacts stacked last with their heading already marked released — `CHANGELOG.md` is never edited after a release — a GitHub Release, and tags without a `v` prefix, as every tag since 0.1.0 has been. Its changelog instruction points at `## [Unreleased]`, and it no longer points at a `validate-cortex.sh` that was planned for 0.3 and never written.
